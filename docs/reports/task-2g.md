The base schemas require UUIDs for student and subject IDs ([studentSchema.ts](../../src/schemas/studentSchema.ts:9), [studentSchema.ts](../../src/schemas/studentSchema.ts:50)). Backup validation deliberately replaces those ID fields with non-empty strings ([backupValidation.ts](../../src/utils/backupValidation.ts:6)), so the UUID requirement is **not** enforced for backup IDs. This preserves the timestamp-style IDs generated by the bulk import flow. No other current source usage of these three schema constants was found.

### Plausible older backups rejected by current validation

The validator accepts omitted optional settings fields, and `examType` is defaulted by the schema, so those omissions are not rejected. It rejects backups that omit required settings fields:

| Older backup shape | Exact current message |
|---|---|
| Missing `schoolName` | `Settings are invalid: Required` |
| Missing `academicYear` | `Settings are invalid: Required` |
| Missing `classScoreMax` | `Settings are invalid: Required` |
| Missing `examScoreMax` | `Settings are invalid: Required` |
| Missing `defaultSubjects` | `Settings are invalid: Required` |
| Uses an old/renamed field instead of one of the required fields above | The corresponding `Settings are invalid: Required` message |
| Student has a missing or empty ID | `Student at index N is invalid: Invalid student ID` |
| Subject has a missing or empty ID | `Student at index N is invalid: Invalid subject ID` |

Other schema-invalid legacy values are also rejected with `Settings are invalid: <first zod issue message>` or `Student at index N is invalid: <first zod issue message>`. Examples include an unsupported `gender`, invalid school level/type/term, invalid academic-year format, or an invalid `examType`. The validator removes only an empty legacy `logoUrl` before parsing ([backupValidation.ts](../../src/utils/backupValidation.ts:27)).

`recordBackup()` is called after the common file-generation path ([DataBackup.tsx](../../src/components/DataBackup.tsx:106), [DataBackup.tsx](../../src/components/DataBackup.tsx:130)). Encrypted exports pass through that same path, so encrypted exports also call `recordBackup`, but only after encryption and file creation succeed.

## Duplicate student IDs

Duplicate IDs are accepted: validation checks each student’s shape and that its ID is non-empty, but does not check uniqueness ([backupValidation.ts](../../src/utils/backupValidation.ts:17)). The app can store and import such a list, but ID-based editing, lookup, or rendering behavior is potentially ambiguous; this task did not add rejection or deduplication.

## Why the blocking overlay is needed

After a successful import, persistence is intentionally suspended until reload, so pending provider debounces cannot overwrite the imported records.  
The overlay prevents users from making edits that would otherwise be silently dropped while persistence is suspended; it offers an explicit reload action as well as the automatic reload.
